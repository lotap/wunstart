# Auth module contract

Auth is a whole module, not a collection of tables. Its models, ops, and invariants are owned here; app wiring (server fns, routes, cookies, middleware) upholds them — see the wunstart skill for that side.

## Composition

Models: `users`, `sessions` (+ `sessions---users` join queries), `anons`, `email-verifications`, `bans`, `activities`, `activities---bans`. Ops: the auth op directory, including its `email/` subdirectory.

## Copy

State-specific auth copy reused by ops and their server functions lives in `_messages.ts`; client-matched contract strings live host-side (`isomorphic/auth-messages.ts`). Anti-enumeration is within-flow: every sensitive branch in one flow returns the same message, status, and timing; cross-flow wording may coincide. Pre-auth flows keep their own copy because their wording differs.

## Strategy

Hybrid: DB-backed `sessions` rows keyed by random token + short-lived stateless access JWT (~15 min) + long-lived refresh JWS (~30d sliding, no absolute max). Access tokens skip DB round-trips; refresh validates against DB for revocation (ban, sign-out). Self-rolled, not a provider: zero vendor lock-in, ban hooks inline. Pure JWT rejected (no revocation); pure sessions rejected (DB lookup per fetch).

## Rotation

Refresh JWS carries `sessionId`, random nonce, `exp`, signed `generation` (see `refresh.ts`). Every authoritative rotation: CAS-advances `refresh_generation` (guarded by expected generation + nonce hash + `revoked_at IS NULL` + `expires_at > now()`), slides expiry exactly 30 days (JWS `exp` + DB `expires_at` + cookie derive from the one committed value — callers pass through, never recompute), keeps one bounded grace slot (prev generation + encrypted previous/successor nonces + 30s). Replay of prev-gen within grace returns the already-created successor without rotating (covers concurrent / response-loss retries), and only when the presented nonce matches the prev-gen nonce inside the grace JWE (`timingSafeEqual`). Valid older-than-prev or expired-grace prev-gen use atomically revokes the family (`revoked_at`, grace cleared), records `REFRESH_TOKEN_REUSE`, clears cookies. Future-gen / bad-signature rejected without revoking. An undecodable grace token (rotated/removed secrets or a corrupt row) is an auth failure at weight 0, not an `INTERNAL_ERROR`, so `verifyAuth` clears the cookies instead of looping on 503. Sign-out / sign-out-all archive sessions; end recorded by `AUTH_SIGN_OUT` / `AUTH_SIGN_OUT_ALL`. A `signOut` token more than one generation stale clears the auth cookies without archiving the row (it cannot prove the nonce); the orphan expires with the session, and presenting it again later reaches refresh’s family revoke.

Accepted limitation: access tokens carry no session id, so family revocation leaves already-issued access tokens valid up to 15 min. The live-session check on account-state, account-email, and other-session ops closes that window at the next action, and reverify checks before minting a replacement token. `signOutAll` also binds the refresh session to the access-token user so mixed cookies fail closed.

## Token secrets

Each token type derives its key with an HKDF purpose tag (`TokenPurpose`: `access`, `refresh`, `refresh-grace`, `anon`), so a key derived for one purpose cannot decrypt or verify another even when secrets are later shared. Purpose tags do **not** protect a leaked master secret: the HKDF `info` string is public, so anyone holding one raw secret can derive every purpose key. Production requires four distinct `*_SECRETS` sets per environment and per database, never reused across environments; the generator is deferred to deployment work. Matching `.env.development` values are accepted because that file is development-only.

## External capabilities

Auth ops consume two host-provided capabilities as Effect service tags and never construct them:

- `EmailService` (`{send}`) — consumed by sending ops, layer provided per run by the caller. The tag lives host-side today (`src/email/service.ts`), and the ops also reach other host modules (e.g. `#/email/templates/…`, `#/email/format-location.ts`); resolve every host import the installed ops carry — typecheck is the check, not a list in this file. The layer (transports, fallback chain) stays host-owned permanently — it is runtime-bound (dev Mailpit, prod Workers `send_email`, optional fallback HTTP transport, bindings) and cannot move.
- `HashingStub` (Durable Object stub) — tag + layer factory live op-side (`db/ops/service-bindings.ts`); the `cloudflare:workers` import stays lazy so the module remains importable (type-only) outside the Workers runtime. This is the pattern to follow: tags travel with the module, implementations stay with the host.

Rule of thumb: if it touches the network, the runtime, or credentials, the implementation is host-owned; the tag is the contract.

## Invariants (db-side, wiring upholds)

- **Eviction is all-or-own.** `sign-out.ts` ends your own current session; `sign-out-all.ts` archives all of the user's sessions and first re-verifies the caller's live session + refresh nonce (current or grace generation) and that the refresh session belongs to the user the access token proved, so mixed cookies fail closed and a post-eviction access token cannot loop the eviction. No user-facing per-session revoke of other sessions: a stolen cookie lets an attacker run a watcher loop auto-revoking each fresh session the victim creates, so the victim never holds a session long enough to invoke `signOutAll`. `signOutAll` is safe because it is indiscriminate — it kills the attacker's session too, and without credentials they can't return. Selective revocation exists only server-side: refresh-reuse detection (`revokeForReuse` in `refresh.ts`, unexported) + owner-email flows. Revisit per-session revoke only alongside unauthenticated email-verified recovery, with remote-revocation email + per-user rate limit + revoke-others-only. Enforced app-side by `wunstart/no-single-session-revoke`.
- **Email enters ops only as a consumed service.** Any op that sends does `const {send} = yield* EmailService` and never constructs or provides the live layer — the caller (server fn / middleware) provides it, so every send site is an explicit layer pass visible in review. Enforced app-side by `wunstart/email-layer-allowlist`.
- **Anon registration is a claim, not a guarantee.** `registered: true` is signed but can outlive its `anons` row (cross-database dev cookie, branch reset, archive race). `emailRequestPasscode` checks the live row before hashing and fails `ANON_NOT_FOUND` at weight 0; `handleEmailRequestPasscode` mints and registers a fresh anon (new id, never the stale one) and retries once. A second miss clears the anon cookie and returns a recoverable 400 instead of looping. `retireAnon` falls back to an existing archive row or archives from the token’s metadata, so sign-in/up never fails on a stale cookie. The FK remains the race backstop. Anon archive rows are append-only: a replayed cookie or a concurrent recovery can retire the same id more than once, so multiple archive rows are valid; `archiveSelectByActiveId` takes the newest by `archive_id`. Do not add a unique index on `anons_archive.id` without handling re-creation.
- **`registerAnon` skips its own ban pre-check.** It runs immediately before `emailRequestPasscode` in the same request, and that op does the check; a second 12-arm query would double first-visit cost for no coverage. Do not add one.
- **Sudo is a 5-minute lease enforced op-side.** `SUDO_EXPIRATION_WINDOW` (`consts.ts`, 5 min); reverify mints a fresh access token carrying `sudoExpiresAt` (`password-reverify.ts`). Sudo-gated ops reject stale verification with `STALE_VERIFICATION` — the name alone grants nothing; authorization is review-enforced. Any op that mutates account state or sends account email also calls `verifyLiveSession` at entry (PK lookup only, no Argon2); so does reverify before it mints a replacement token. `signOutAll` gets the same guarantee from the refresh-session check it already runs for the nonce and grace generation. A missing/revoked session keeps `userId` attribution but logs at weight 0 (ordinary after a remote sign-out or password change elsewhere), while a token/session user mismatch is charged. The read-only email lookup is the deliberate exception — sudo-only, no session lookup, so Settings does not pay one per render. Sign-in grants the lease because re-entering the same password seconds later adds no protection; requiring email verification for all sudo is deferred until a lost-old-email recovery path exists. Wiring (provider timestamp + expiry timer + reverify drawer) lives in the wunstart skill.
- **Sign-in latency is uniform.** `passwordSignIn` runs the `FAILED_CREDENTIAL` pre-check before looking for a password, then performs an Argon2 verify for unknown users and passwordless users too, against `DUMMY_ARGON2_HASH` (parameters interpolated from `HASHING_CONFIG`) sharded on the Anon. Never early-return before hashing: the ~700 ms delta is an account/password-status oracle. The ban check also bounds dummy DO work per credential (four failures per window); it is not a global DO-CPU bound.
- **Denial weight routes to IP scope.** Rate-limit denials never persist `failedCredential` — pass the email as `meta: {credential}` for audit only. See `references/bans.md`. Enforced by `wunshot/no-failed-credential-in-denial`.
