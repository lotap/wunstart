# Auth module contract

Auth is a whole module, not a collection of tables. Its models, ops, and invariants are owned here; app wiring (server fns, routes, cookies, middleware) upholds them — see the wunstart skill for that side.

## Composition

Models: `users`, `sessions` (+ `sessions---users` join queries), `anons`, `email-verifications`, `auth-attempts`, `bans`, `activities`, `activities---bans`. Ops: the auth op directory, including its `email/` subdirectory.

## Copy

State-specific auth copy reused by ops and their server functions lives in the ops' shared copy module; client-matched contract strings live host-side. Anti-enumeration is within-flow: every sensitive branch in one flow returns the same message, status, and timing; cross-flow wording may coincide. Pre-auth flows keep their own copy because their wording differs.

## Strategy

Hybrid: DB-backed `sessions` rows keyed by random token + short-lived stateless access JWT + long-lived refresh JWS (sliding, no absolute max). Access tokens skip DB round-trips; refresh validates against DB for revocation (ban, sign-out). Self-rolled, not a provider: zero vendor lock-in, ban hooks inline. Pure JWT rejected (no revocation); pure sessions rejected (DB lookup per fetch).

## Rotation

Refresh JWS carries `sessionId`, random nonce, `exp`, signed `generation`. Every authoritative rotation CAS-advances `refresh_generation` (guarded by expected generation, nonce hash, `revoked_at IS NULL`, and `expires_at > now()`), slides expiry to the configured session lifetime (JWS expiry, DB expiry, and cookie derive from one committed value — callers pass through, never recompute), and keeps one bounded grace slot (previous generation, encrypted previous/successor nonces, short window). Replay of the previous generation within grace returns the already-created successor without rotating (covers concurrent and response-loss retries), and only when the presented nonce matches the previous nonce inside the grace JWE. Valid older-than-previous or expired-grace tokens atomically revoke the family, record a reuse failure, and clear cookies. Future-generation and bad-signature tokens are rejected without revoking. An undecodable grace token (rotated/removed secret or corrupt row) is an auth failure at weight 0, not infrastructure, so the auth middleware clears cookies instead of looping on 503. Sign-out and all-device sign-out archive sessions. A local sign-out token more than one generation stale clears the auth cookies without archiving the row (it cannot prove the nonce); the orphan expires with the session.

Accepted limitation: access tokens carry no session id, so family revocation leaves already-issued access tokens valid until they expire. The live-session check on account-state, account-email, and other-session ops closes that window at the next action, and reverify checks before minting a replacement token. All-device sign-out also binds the refresh session to the access-token user so mixed cookies fail closed.

## Failure policy

Token and session failures are classified before policy: expired, rotated-out (`kid` absent from the secret map), known-kid verification failure, dead or revoked session, wrong nonce, future generation, reuse replay, token/session user mismatch, and completed local sign-out are distinct states. A token/session user mismatch gets its own `SESSION_USER_MISMATCH` activity cause; a missing row keeps `SESSION_NOT_FOUND`, so audit can distinguish them. Outside grace, among token verdicts, a known-kid verification failure is charged; expired and rotated-out verdicts are weight 0, except that the Anon map defines an expired row at the invalid charge for a future `exp` claim. The unauthenticated refresh entry also charges a wrong nonce (`attemptRotation`, `replayFromGraceToken`) and a future generation (`classifySession`); a reuse replay revokes the family and logs at `ACTIVITIES_BASELINE_WEIGHT`, and a missing session is weight 0. Sign-out, sign-out-all, and the live-session check charge no nonce check failure. A token/session user mismatch and a completed local sign-out are weight 0. An undecodable grace token is weight 0. A missing or malformed header is not a rotation state and takes the entry's invalid behavior. An unknown `kid` is treated as a rotation state because a forged header is indistinguishable; request-level lanes bound repeated weight-0 attempts.

Cookie behavior follows the outcome class: an auth-token failure clears or falls through at the auth boundary, a dead-session failure clears the pair, a local sign-out completes, and a strict all-device sign-out surfaces the error and keeps the pair. HKDF and unexpected internal state are infrastructure, never token verdicts: weight 0, cookies kept, degraded or failed request. Ban and limiter refusals are control failures, not token verdicts: they keep cookies and continue as Anon where identity resolution still applies.

Exact causes, allowances, messages, classes, and per-context maps live in code; consumers that need values import them. This section states the classification rule, not the values.

## Token secrets

Each token type derives its key with an HKDF purpose tag (`TokenPurpose`: `access`, `refresh`, `refresh-grace`, `anon`), so a key derived for one purpose cannot decrypt or verify another even when secrets are later shared. Changing the HKDF `info` string, a secret value under an existing `kid`, or the payload shape invalidates every token of an affected type minted before the deploy. The old `kid` still resolves, so access, refresh-entry, and anon failures are charged as failed credential presentations, not the weight-0 unknown-kid state (an undecodable grace token is weight 0). Ship such a change atomically with a new `kid` for each affected token type and remove the old one; keeping the old `kid` in the map does not help, because it derives the new key and fails the same way. Removing it classifies returning clients as the weight-0 rotation state instead of accumulating an IP ban that also blocks their re-login. Purpose tags do **not** protect a leaked master secret: the HKDF `info` string is public, so anyone holding one raw secret can derive every purpose key. Production requires a distinct `*_SECRETS` set per token purpose, environment, and database, never reused across environments.

## External capabilities

Host-provided capabilities are consumed as Effect service tags and never constructed:

- `EmailService` (`{send}`) — consumed by sending ops, layer provided per run by the caller. The tag is host-provided, and the ops also reach host email modules for rendering and location formatting; resolve every host import the installed ops carry — typecheck is the check, not a list in this file. The layer (transports, fallback chain) stays host-owned permanently — it is runtime-bound (dev Mailpit, prod Workers `send_email`, optional fallback HTTP transport, bindings) and cannot move.
- `HashingStub` (Durable Object stub) — the tag + layer factory travel with the op module; the runtime import stays lazy so the module remains importable (type-only) outside the Workers runtime. This is the pattern to follow: tags travel with the module, implementations stay with the host.

Rule of thumb: if it touches the network, the runtime, or credentials, the implementation is host-owned; the tag is the contract.

## Invariants (db-side, wiring upholds)

- **Eviction is all-or-own.** Single-session sign-out ends your own current session; all-device sign-out archives every session for the user and first re-verifies the caller's live session, refresh nonce, and user binding, so mixed cookies fail closed and a post-eviction access token cannot loop the eviction. No user-facing per-session revoke of other sessions: a stolen cookie lets an attacker run a watcher loop auto-revoking each fresh session the victim creates, so the victim never holds a session long enough to invoke all-device sign-out. All-device sign-out is safe because it is indiscriminate — it kills the attacker's session too. Selective revocation exists only server-side: refresh-reuse detection plus owner-email flows. Revisit per-session revoke only alongside unauthenticated email-verified recovery, with remote-revocation email, per-user rate limit, and revoke-others-only. Enforced app-side by `wunstart/no-single-session-revoke`.
- **Email enters ops only as a consumed service.** Any op that sends does `const {send} = yield* EmailService` and never constructs or provides the live layer — the caller (server fn / middleware) provides it, so every send site is an explicit layer pass visible in review. Enforced app-side by `wunstart/email-layer-allowlist`.
- **Anon registration is a claim, not a guarantee.** `registered: true` is signed but can outlive its anon row (cross-database dev cookie, branch reset, archive race). The passcode request checks the live row before hashing and fails at weight 0; the caller mints and registers a fresh Anon (new id, never the stale one) and retries once. A second miss clears the anon cookie and returns a recoverable 400 instead of looping. Retiring an Anon falls back to an existing archive row or archives from the token's metadata, so sign-in and sign-up never fail on a stale cookie. The FK remains the race backstop. Anon archive rows are append-only: a replayed cookie or concurrent recovery can retire the same id more than once, so multiple archive rows are valid; selection takes the newest by archive id. Do not add a unique index on the active id without handling re-creation.
- **Sudo is a short lease enforced op-side.** Reverify mints a fresh access token carrying `sudoExpiresAt`. Sudo-gated ops reject stale verification — the name alone grants nothing; authorization is review-enforced. Any op that mutates account state or sends account email also runs the shared live-session check at entry (PK lookup only, no Argon2); so does reverify before minting. All-device sign-out gets the same guarantee from its refresh check. Inside authenticated checks, use the failure policy above: live-session rows keep `userId` at weight 0; all-device sign-out uses the strict rows. The unauthenticated refresh op charges a known-kid invalid JWS and leaves expired or rotated-out tokens at weight 0; request-level lanes bound that loop. The read-only email lookup is the exception — sudo-only, no session lookup, so Settings does not pay one per render. Sign-in grants the lease because re-entering the same password seconds later adds no protection; requiring email verification for all sudo is deferred until a lost-old-email recovery path exists. Wiring (provider timestamp + expiry timer + reverify drawer) lives in the wunstart skill.
- **Sign-in latency is uniform.** Password sign-in runs the failed-credential pre-check before looking for a password, then performs an Argon2 verify for unknown and passwordless users too, against a dummy hash with the configured parameters. Never early-return before hashing: the timing delta is an account/password-status oracle. The auth attempt allowance (`models/auth-attempts/`, reserved before the hash) bounds dummy work per credential; the ban pre-check is a read and cannot bound a concurrent burst.
- **Denial weight routes to IP scope.** Rate-limit denials never persist `failedCredential` — pass the email as `meta: {credential}` for audit only. See `references/bans.md`. Enforced by `wunshot/no-failed-credential-in-denial`.
