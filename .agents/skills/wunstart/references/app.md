# App: routes, frontend, runtime

## Routes (TanStack file-based)

- `_`-prefixed dirs = pathless layouts; `-`-prefixed folders/files = private to their route/layout, not routed. Never edit `routeTree.gen.ts` (restart dev — the TanStack Start plugin regenerates it, type registration included).
- `_auth-*` placement IS the guard — moves across folders are security-relevant in review: `_auth-protected` (requires sign-in, redirect `/sign-in?redirect=`, wraps `HasSudoProvider`), `_auth-gateway` (auth-flow only, sign-in/up, authed bounce `/`), `_auth-dynamic` (no redirect, adapts; marketing that changes its call by auth — e.g. pricing with manage-vs-buy CTA; `HasSudoProvider key={auth ? 'user' : 'anon'}` resets stale sudo), `_auth-anon` (no guard/provider — public pages where auth state is irrelevant, e.g. static pricing). Layout `route.tsx` often comment-only docs of the implied protection.
- Dev-only page: place it under the pathless `_dev` layout (`routes/_dev/route.tsx`). Production builds generate `.tanstack/routeTree.prod.gen.ts` with `_dev` excluded (`vite.config.ts`) and redirect the router import to it, so the route record itself is absent; the layout's `beforeLoad` still throws `notFound()` off-dev as defense in depth. Keep the heavy implementation in the route's private `-components/` and import it inside `import.meta.env.DEV` (`routes/_dev/docs/route.tsx` → `docs/-components/docs-page.tsx`) so it is tree-shaken even if the route tree regresses; never inline it into the route file or import it statically. Do not put it in the product header nav; link it from the README or a dev-only utility. A dev-only page must not drive product chrome. The in-repo docs page (`/docs`) is the developer-facing reference, extended through `docs/-components/feature-explorer/`; getting-the-checkout-running steps stay in the README and agent rules in these skills.
- Chrome: `Header`/`Footer` mount in the `__root` shell (`components/global/header/header.tsx`, `components/global/footer/footer.tsx`); the footer receives the resolved audience, while the header branches only on `context.auth`. The 404 is `components/global/status-pages/not-found.tsx`; unmatched and not-found matches resolve to `adaptive` audience, so anons get the external footer and signed-in users the internal one. Route errors use `components/global/status-pages/route-error.tsx`; both share the private `components/global/status-pages/_status-page-frame.tsx`, both are `noindex`, and error matches keep the route’s audience. Preview both at `/status-pages` in dev (`routes/_dev/status-pages/`). Chrome edits render on every route — verify across layouts and both identity modes.
- Header customization lives in the header folder: `_links.ts` (signed-out/signed-in link arrays; add a `to` route and the link type validates it), `_nav-link.tsx` (the single page-link voice and active underline), `_github-link.tsx` (the project’s repo action, signed-out only), `_header-menu.tsx` (the menu below `md`: links, GitHub, theme, account, and auth), `_account.tsx` (the signed-in menu’s account block and sign out). The header is auth-only with a constant 64px desktop / 56px mobile height; the page audience belongs to the footer. The signed-out header carries the project’s GitHub action (icon on `md` and up, menu action below); the signed-in header and the internal footer carry none. `PUBLIC_REPO_URL` in `src/repo.ts` (project config, deliberately outside `appInfo`) drives the header action, menu row, external footer Connect column, and license line; `null` removes all four together. At `md` and up the bar holds the utilities: repo icon, theme, divider, then Sign in / Sign up (or the account avatar); below `md` those controls move into the menu, and the bar keeps only the brand and the trigger. The menu is one centered block above an anchored auth pair: page links → GitHub (word plus external mark) and Theme (icon adjacent) → a ghost Sign in over a default Sign up, 56px each and 12px apart, for anons; the signed-in menu is links → the account block (a muted “Signed in as” label above the email, which truncates on its own line, plus Preferences, Profile, and Access & Security with the dropdown’s icons) → Theme, with a ghost Sign out in the anchored slot. There is no divider or custom CTA. The theme control means the trigger always renders below `md`, so the menu is never empty. Below `md` the menu is one full-bleed sheet under the header with page scroll locked; the content is a centered `max-w-md` block: 30px page links at 52px rows, a 64px gap, then GitHub and Theme at 16px/44px rows. Sign in and Sign up anchor the bottom as stock 56px ghost/default buttons on separate rows; signed in, the account shortcuts join the same group and a ghost Sign out takes the anchored slot. No divider or custom CTA; the content is centered once there’s room. Sizes come from the theme scale (`text-3xl`, `h-13`, `mt-16`, `h-14`), never hand-picked pixels or arbitrary rem values. Hover is the text color alone, never a row fill; the rows inset 8px into the gutter so the focus ring clears the label while labels stay on the 24px line. The desktop list appears at `md` and is centered by default; `justify-self-*` moves the group, and the bar holds about four typical signed-out links before the actions need room; for five or six, move the breakpoint to `lg` or use a More menu. The header is sans and static on the three-slot grid; `sticky top-0` is opt-in (offset the landing dock if both). User-facing version: `/docs` guide “Customize the header”.
- Page metadata and headings: every route owns its `head` title/description (through `lib/page-meta.ts`) and its `h1`; the header wordmark is a `div`, never a heading. `__root__` supplies the fallbacks, the canonical link, `og:site_name`/`og:type`, and the request origin (`lib/site-origin.ts`); the home route owns the `WebSite`/`Organization` JSON-LD, driven by `appInfo`. New pages copy the shape from the docs guide “Start a new page”.
- Auth verified exactly once in `__root.tsx` `beforeLoad` → `handleVerifyAuth()` (returns only `{sudoExpiresAt?}`, no db ids to client). Layouts read `context.auth`; never re-call in children. Data via `useQuery` + `useServerFn`; loaders allowed where SSR/first-paint/SEO wins (public content), keeping auth verify in `beforeLoad` only. `validateSearch` also via `Schema.toStandardSchemaV1`. Db ids never travel client→server (path, search, or fn input) — identity unwraps from cookies; non-id params (slugs) allowed via validated search/path.
- Settings nav: register in `routes/_auth-protected/settings/-categories.ts` (`CATEGORIES`, section-component-free); components attach in `-components/page.tsx`. Registry exception: the menu must not pull section components into its bundle, so metadata stays component-free and the page owns the map. The account shortcuts keep their own curated list in `components/global/header/_settings-shortcuts.ts`, shared by the desktop dropdown and the menu, instead of importing the settings module: it is a curated subset, its literal ids are checked by the settings route’s search schema, and global chrome never imports a route folder.
- Drawers: self-contained components with trigger props (`PasswordChangeDrawer triggerClassName/triggerVariant`, composed in `access-and-security.tsx`); lazy-load when heavy (`routes/_auth-dynamic/(home)/-components/dashboard/dashboard.tsx` → `welcome-drawer.tsx`). One-shot post-action UX via a `useLocation().state` flag cleared with `navigate({to, state})` on dismiss.

## In-repo docs

`/docs` has three surfaces: guides (task walkthroughs), reference panels (topic docs), and feature panels (product catalog). Every panel is a component, content lives with the panel, and the explorer lists panels.

- Guides are task walkthroughs. Reference panels are topic docs. Feature panels are the product catalog.
- `feature-explorer/` mirrors the sidebar: `features/`, `reference/`, and `guides/`, with `feature-explorer.tsx` at the root. Put a new panel in the matching folder.
- `feature-explorer.tsx` owns the three lists (`guidePanels`, `referencePanels`, `featurePanels`). Order is intentional: Features and Reference are alphabetical by label; Guides follow task order (Start a new page, Customize the header, Worktrees, Database migrations). The lists hold labels and panel components, and each panel owns its content. There is no separate feature registry. Selection lives in the route’s `?panel=<group>.<key>` search param (`reference.auth`, `feature.images`); the group travels in the value because keys repeat across surfaces, and an unknown value falls back to the first guide. Panel links carry the group too, and each side list only sees its own group’s active key. The page owns its scroll: `/docs` opts out of router scroll restoration; on arrival an effect scrolls to the hash, then the explorer when the URL names a panel, otherwise the top; later panel switches scroll the explorer smoothly. Panel navigation skips the view transition.
- Feature tabs are components in `docs/-components/feature-explorer/features/`. A feature component composes `FeatureShell` (header only) and owns its children.
- Planned features are components too. Compose `PlannedFeatureShell` with the feature name, summary, and what is missing.
- Shared blocks live in `feature-explorer/feature-blocks.tsx`: `FeatureActions` and `FeatureFlows` render structured data, `FeatureShell` and `PlannedFeatureShell` are headers. Everything else is composed from docs primitives: `PanelSection` (title + children), `Prose` (paragraph style), `DocDiagram` (static Peel source), `PromptBlock`, `PanelLink`, `PanelReferences`.
- `PanelSection` is a skin, not a content model. Pass content as children; do not add per-section description or wrapper props.
- Do not add per-feature fields to the shell. If a block appears in every feature, make it a shared block; otherwise write it in the feature file.
- Do not create feature-specific content wrappers. Compose the section from shared primitives; if a visual pattern repeats, extract only the skin, not the content sequence.
- The same rule applies outside feature panels: `Shortcut` (local dev) and `PromptBlock` are skins; callers compose the surrounding sequence.
- A feature with reference depth links to its reference panel (`PanelLink`). The feature tab repeats only the detail the basic task needs; the reference owns internals, edge cases, and rejected options.
- Reference panels are components under `docs/-components/feature-explorer/reference/`; they own their topic docs and may use JSX directly.
- Panel content stays with its panel. Do not recreate a shared `-content` registry for docs prose. Genuinely shared runtime values, such as the local service URLs, live in `docs/-utils/`, not `-content/`.

## Adding a page

Pick `_auth-*` placement → `handle-*.ts` (shape: see `references/middleware.md`) → `queryOptions` beside the feature (shared ones in the owning domain’s `_utils.ts` while small, then a named `_<topic>` module; keys `['<thing>', ...params]`, e.g. `['passcodeRequest', email, intent]`) → reads via `useQuery` + inline pending/error inside `ErrorBoundary` (search via `Route.useSearch`) → navigate via `router.navigate({to, state})`; button-styled links via `RouterButton`, text links via `Link`; never `<a href>` for internal routes or `Button`+onClick nav → restart dev (regenerates routes) → verify (`bun run check`). Auth changes end with `router.invalidate()`. Exemplars: list query `settings/-components/sessions.tsx`, page with search `settings/`, sudo-gated mutation `components/auth/remove-account.tsx`, email flow `components/auth/email-change.tsx`.

## Frontend

- React Compiler ON (babel preset in `vite.config.ts`): zero `useMemo` / `useCallback` / `React.memo` in hand code. Don't hand-memoize.
- New files use named exports; default only where an external consumer requires it (e.g. email templates for email dev, `server.ts`, `theme-toggle.tsx`, `root-provider.tsx`, `integrations/tanstack-query/devtools.tsx`, `form-fields/password-strength-meter.tsx`).
- Zero `React.FC` — prefer inline `props: {...}` object types over `interface` (pre-existing infra `interface`s are grandfathered). `React.ReactNode` via global namespace, no React import. No `"use client"` in hand code.
- Optimistic updates encouraged for reversible product mutations (rollback on error, reconcile with server value); auth/security/ban paths stay invalidate-then-refetch — never guess server-computed values (one exception `setQueryData` with server-computed value on mutation success).
- Feedback: forms → `OnSubmitErrors`; non-form mutations → `toast` (`components/ui/toast.tsx`); reads → inline pending/error inside `ErrorBoundary` (route-level `errorComponent: RouteError` + `notFoundComponent` live in `__root`). `AsyncBoundary` wraps a lazy/async subtree in both so a failed query or chunk load degrades locally instead of unmounting the page. Unknown data on first load → inline `Skeleton` sized to the expected content so layout never shifts (match w/h to the value, comment the match); sections/forms mirror shape with stacked `Skeleton`s in place; never blank, spinner-only, or guessed values.
- Contexts recipe: `createContext<T | null>(null)` + throwing `use*` hook + `PropsWithChildren` provider. Theme tri-state (`null` = not hydrated; consumers must handle). Query client via `integrations/tanstack-query/root-provider: getContext() → {queryClient}`.
- shadcn on Base UI (`@base-ui/react`), cssVariables. Current install choices — `base-nova` flavor, neutral base, lucide icons — are swappable identity, not constraints; change freely for your own look. `src/components/ui/**` generated — don't edit; override from caller via `cn()`; patch only for new export/variant/behavior, minimal. Caller pattern `render={<X />}` never `asChild`; `render={<Link to=… />}` works. Icons via `lucide-react` today (`data-icon` pattern per shadcn skill). Three-way split: behavior modes get explicit components (never boolean mode props); style variants get CVA props; booleans carry data/state only (`isPinned`, `isCurrent`).
- Forms (`hooks/use-app-form.ts`, TanStack Form alpha): `createFormHook({fieldComponents: CheckboxField/EmailField/PasscodeField/PasswordField, formComponents: SubmitButton/OnSubmitErrors})`; `useConfiguredAppForm({defaultValues, onSubmitTry, onSubmitSchema: ConstraintCodec})`, `validateAfterFirstSubmit` (silent until attempts > 0, then change + blur). Fields take `{field: FieldWithValue<string>}`, `isTouched && !isValid`, `ui/field` + `input`/`input-group`, sr-only labels, `aria-invalid`/`describedby`, min/maxLength mirrors schema. Shared `passcodeRequestQueryOptions` / `userProfileQueryOptions`; localStorage email/step with `DateTime` + 24h.
- `useLocalStorageQuery({key, schema})`: Query over localStorage (`[localStorage, key]`, Infinity stale), schema-validated, `Expiry.expiresAt` eviction, merge-mutate + cross-tab invalidate.
- Styling: Tailwind v4 CSS-first (`styles.css`): oklch vars `:root` / `.dark`, `@theme inline`, `@custom-variant dark`, Inter Variable, view-transition on main + reduced-motion guard. `cn()` from `'cn'` (`#/lib/utils.ts` is only a re-export shim); oxfmt sorts Tailwind (stylesheet `styles.css`, functions `[clsx, cn]`). Stock shadcn token names only. Run `bun run lint:tailwind [paths…]` for the editor’s IntelliSense diagnostics (canonical classes, conflicts, variant order); it defaults to `src/`, skips generated `ui/**` (add `--include-generated` to inspect it), and is separate from oxlint.
- `src/isomorphic/` stays pure es2022 (no node/browser): Email (trim + lower + 254 + regex) / Password (8char + NFKC + 72B) / Passcode (`/^\d{6}$/`), one export per shape in `validations/auth.ts`, `mask-email` (`j***@domain`), zxcvbn lazy dicts `MIN_SCORE = 3` + `[<your product name per CONTEXT.md>, ...userInputs]`. Shared client + server via `toStandardSchemaV1`.

### Component placement

- Co-location is the default: a value, helper, or piece of copy lives with the module that owns it. Move it out for a named second consumer or a size threshold, and treat a registry as an exception with a reason.
- `src/components/` contains domains and `global/` only, no loose files. Domain folders (`architecture/`, `auth/`, `form-fields/`, `ui/`) own code shared within that domain. `global/` owns app chrome or domain-agnostic infrastructure: mounted from `__root`/`router.tsx`, or primitives used across unrelated domains (`header`, `footer`, `not-found`, `theme-toggle`, `router-button`, `route-error`, `error-boundary`, `async-boundary`, `copy-button`, `external-doc-link`). It is not a home for shared product features.
- Within a domain folder, the unprefixed file is the entry point; `_`-prefixed files are private to that folder. Consumers outside the folder import only the unprefixed entry. `auth/` exemplars: `sign-up-form.tsx` / `sign-in-form.tsx` consume `_passcode-form.tsx`, `_form-heading.tsx`, `_hooks.ts`, `_utils.ts`. `global/footer/` follows the same shape: `footer.tsx` is the only exported entry, with `_external-footer.tsx`, `_internal-footer.tsx`, `_footer-utility.tsx`, `_footer-image.tsx` private beside it. The prefix is a review signal, not an import restriction.
- A shared feature belongs to its permanent domain even when multiple routes use it. Example: `components/architecture/framework-shelf.tsx` is used by the docs page and previewed on the landing page. A starter page may import it temporarily; mark the preview for removal instead of moving the component.
- A named route gets its own directory: `<segment>/route.tsx` plus private folders as needed (`-components/`, `-hooks/`, `-utils/`, `-content/`; `-` keeps them out of the route tree). Examples: `_auth-protected/settings/route.tsx` + `-components/`, `_auth-anon/landing-page/route.tsx` + `-components/`, `-hooks/`, `-utils/`. `route.tsx` is the segment route (layout/guard); use it for a named page even without children. `index.tsx` is the default child matching the parent path exactly; use it when the segment has a layout with siblings, or for a pathless index group (`(home)/index.tsx`). A leaf named page does not become `index.tsx`.
- An index route gets a pathless route group directory: `(<page>)/index.tsx` plus private folders as needed. The group is organizational; the URL remains the parent path. Example: `_auth-dynamic/(home)/index.tsx` still serves `/`.
- A layout-level `-components/` is only for code shared by that layout’s routes. Index-page code goes in its `(<page>)/-components/`, not the layout root.
- When one route renders distinct runtime branches, keep one route file and split private components by branch under its `-components/` (e.g. `(home)/-components/anon/`, `(home)/-components/dashboard/`). Never create separate routes for runtime auth/state branches.
- Do not import another route's private folders directly. Promote on the second consumer: one route → route-private; shared feature → its owning `components/<domain>/`; domain-agnostic infrastructure → `components/global/`.
- Do not create speculative page folders under `src/components/`. A `landing/`, `home/`, or similar folder appears only after a second route needs the same components.
- The same ownership rule applies to hooks and utils: route-specific ones live in peer `-` folders beside `-components/`, never nested under `-components/`. A pure util with one consumer stays in its component; extract it to `-utils/` on the second consumer. `-utils/` is non-rendered behavior and operational config: pure helpers, calculations, parsers, formatters, layout math, environment shims, service URLs, limits, flags, and commands tied to scripts. Operational values are utils even when a component displays them; the test is what changes them, not whether they appear on screen. A hook that owns an effect lifecycle or imperative DOM work belongs in `-hooks/` even with one consumer, one hook per rendered unit; a trivial state wrapper stays in its component. Placement follows what the module knows, not its consumer count. Route-private behavior (screen rules, observers, rAF, timers, measurement, refs to route elements) stays in the route’s `-hooks/`; a domain-agnostic primitive or environment shim (browser API subscriptions such as `matchMedia`, SSR compatibility such as a `useLayoutEffect`/`useEffect` alias, cross-route client state) lives in `src/hooks/` even with one consumer; a feature primitive shared within one domain lives in that domain’s `_hooks.ts` / `_utils.ts` while it is small; split it into a named `_<topic>` module once it has a distinct concern. Consumer count only promotes route-owned code: a second route importing it moves it to the shared location or its owning domain.
- Split `-components/` by rendered unit (panel, page section, runtime branch), not by helper function. A small helper used by one component stays in that component file.
- A component with private children gets a folder named after it: `<parent>/<parent>.tsx` is the entry, and its private children sit beside it as `_`-prefixed files. Files imported by multiple parent modules stay at the route `-components/` root; don't create a folder for a single child.
- Content starts in the component that renders it. Extract to `-content/` only when a second module needs the same material, or when the data is large enough to bury the component’s markup — a conversation script, a long install command set, a diagram source. A few labels, one prompt, or one component’s copy stays in its component.
- `-content/` is plain authored data: copy, labels, diagram sources, sample conversations, install instructions, and their types. It exports data, not functions; it does not read env, fetch, hold state, or import app code. Presentational JSX is limited to inline emphasis and links built from plain elements — never app UI components. If it needs behavior, layout, a UI primitive, or app state/env, it is a component or a util, not content.
- Do not put component maps, panel registries, or docs prose in `-content/`. A registry belongs with the module that consumes it. Docs panels own their prose; shared operational values such as service URLs and commands live in `docs/-utils/`.
- Import content where it is rendered. Do not thread a `-content` registry through the page or an uninterested intermediate component as a prop; props are for selecting among values, caller overrides, and reusable primitives. A registry owned by one rendered unit imports it directly.
- Registries are exceptions, not a default. Create one only when the key set or order is the consumer’s API — docs navigation, settings categories — and importing every entry would pull the wrong code into the bundle. Keep it beside the consumer and ordered. A navigation registry may hold labels and panel/component references; it must not hold the panel’s prose, nested content, or defaults that could stay with their consumer.
- `src/components/ui/**` stays generated (shadcn). Bespoke shared UI goes in `global/` or a domain folder, never a new hand-written file under `ui/`.

### Page-specific styles

- `src/styles.css` is global-only: theme tokens (`:root`, `.dark`, `@theme inline`), base/reset, fonts, view transitions, and global library themes (`.pele`). No route, page, or feature selectors belong there.
- Tailwind utilities are the default for layout, spacing, typography, color, state, and simple effects. Compose with `cn()`; map state to classes with CVA, not ternaries.
- Keep the class list in the component that renders the element. Do not create `*ClassName` constants or styles-only util modules. When the same look must render through different elements (`p` vs `th`, `a` vs `button`), give each component its own class list; use CVA when one component genuinely has style variants.
- Page/feature CSS that utilities cannot express cleanly goes in a colocated `*.module.css` next to its component and is imported by that component. The usual cases are `::before`/`::after`, `@keyframes`, multi-stop or responsive mask gradients, and vendor-prefixed properties. Reference classes as `styles['name']` inside `cn()` (`noPropertyAccessFromIndexSignature` is on); examples: `grow-next-background.module.css`, `intro-sections.module.css`.
- Keep modules minimal. If a declaration has a utility equivalent, move it back to JSX. A decorative layer that needs clipping gets its own `overflow-hidden` wrapper, so the outer shell can keep overflow visible when content such as an out-of-flow hint must escape it; the module owns only the gradient and keyframes, and the inner surface gets `relative z-10`.
- One-off keyframes and reduced-motion overrides stay in the module. A `@theme` token is global: add one only when the value is shared or belongs to the design system. Single-consumer easings and animations stay inline as arbitrary utilities or in the owning module; promote to `@theme` only when a second feature uses them.
- Do not add route-level plain CSS by default. If a page-wide stylesheet is genuinely unavoidable, prefix its selectors with the route/feature name and import it from that route; a module is still preferred.

### Custom hooks

Shared primitives live in `hooks/`; feature composition in the owning domain’s `_hooks.ts` (see `auth/_hooks.ts`), split into named `_<topic>` modules as it grows.

- Shared client state (e.g. a checkout cart visible on every page): `useLocalStorageQuery({key, schema})` → `{query, mutation, remove}`. Key `['localStorage', key]`, `staleTime: Infinity`, schema-validated reads (malformed/expired → null + evicted), merge-`mutate`, cross-tab invalidation via `storage` events. Same key on any page reads the same state; `mutation.mutate(partial)` from any page updates all mounted readers. Wrap per concern (`useLocalStorageEmail`-style) and stamp `expiresAt` on writes (24h in auth). Shape, following `useLocalStorageAuthFormState`:
  ```ts
  export function useCart() {
  	const {query, mutation, remove} = useLocalStorageQuery({key: 'cart', schema: CartSchema})
  	return {
  		items: query.data?.items ?? [],
  		isPending: query.isPending,
  		upsertItem: (item: CartItem) => mutation.mutate({items: mergeInto(query.data?.items, item)}),
  		clear: remove,
  	}
  }
  ```
- Action hooks follow `use-sign-out`: `useServerFn(fn)` → try → `router.invalidate()` → catch → `toast.add({type: 'error', …})`.
- Context consumers: `useTheme()` gives `theme` (setting, incl. `system`) vs `resolved` (effective light/dark); `null` pre-hydration → render Skeleton; toggle cycles system→flip (see `theme-toggle.tsx`, `contexts/theme.tsx`).

### Form interactions

- `useConfiguredAppForm({defaultValues, onSubmitTry, onSubmitSchema})` with field components (`CheckboxField`/`EmailField`/`PasscodeField`/`PasswordField`). To add a field type, three steps (see `form-fields/email.tsx`): `({field}: {field: FieldWithValue<string>})` component built from `ui/field` + `input` (sr-only label, `isTouched && !isValid`, `aria-invalid`/`describedby`, `FieldError`); register via `fieldComponent.strict(Comp, 'field')` in `hooks/use-app-form.ts`; consume as `<field.XField />` render prop. The registry is the form API; field logic stays in `form-fields/`.
- Validation splits two ways: `onSubmitSchema` (isomorphic `ConstraintCodec`, silent until first submit via `validateAfterFirstSubmit`) checks shape client-side; external checks (e.g. address/zip validation against an API) run server-side inside `onSubmitTry` — throw on failure. Server errors are form-level only (`fields: {}` in `use-app-form.ts`); there is no field-targeted server error path, so design external checks as pass/fail for the whole submission.
- Drafts: prefill `defaultValues` from the localStorage query, persist via its mutation (see sign-up email); multi-step flows keep `step`/`setStep` in localStorage state (`useLocalStorageAuthFormState`).
- Submit through a server fn (`useServerFn`) directly, or a feature mutation (`usePasscodeRequestMutation`-style, `setQueryData` on success).

## Runtime

- `src/server.ts`: Workers entry (`wrangler.jsonc` main) — re-exports `AuthHasher` DO + Start fetch handler + `scheduled` cron (archives old records). Bindings HYPERDRIVE, `send_email: EMAIL`, `AUTH_HASHER` DO + migrations; `env.development.secrets.required` = `*_SECRETS` (`id:secret` pairs); provision the same secrets in prod (`wrangler secret put`) alongside the email config. `src/start.ts`: `createStart` factory (request + function middleware). `src/router.tsx`: router + Query wiring. `cf-typegen` after `wrangler.jsonc` binding change.
- Wasm: `assetsInclude **/*.wasm`, watch ignores `.tmp`.
- Effect services: `Context.Service` + `Layer.effect`, return `Service.of({...})`, `Effect.fn('Service.method')` for tracing, `Schema.TaggedError` errors, `Config.schema(Schema.Literals([...]), 'ENV')` plural-array + typed `withDefault` / `option` / `Redacted`. No keyof casts, no string fail. Lazy `cloudflare:workers` via `Effect.tryPromise(import())`.
- TS v6 tsgo: strict + `noUncheckedIndexedAccess`, `noPropertyAccessFromIndexSignature`, `noImplicitOverride/Returns`, `verbatimModuleSyntax` (`import type` for types), `allowImportingTsExtensions`. `@effect/language-service` downgrades 22 diagnostics to warnings scoped to `src/db/**`. No typecheck script → `bunx tsc --noEmit`.
