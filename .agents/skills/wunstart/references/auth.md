# Auth wiring

Strategy, rotation, eviction posture, email-service and sudo-lease invariants are owned by the wunshot auth contract (`wunshot/references/auth.md`). This file is only the app-side wiring that upholds them.

## Sudo-gated actions

`useHasSudo()` gate + lazy `ReverifyDrawer` inside `AsyncBoundary` (see `remove-account.tsx`); the server fn's op rejects stale verification (`STALE_VERIFICATION` → re-verify first, see `remove-user.ts`). Lifecycle: provider holds the `sudoExpiresAt` timestamp as state (seeded from auth context) with a timer clearing it at expiry; a successful reverify sets a fresh timestamp via `setSudoExpiresAt`. Provider placement: see `references/app.md` routes.

The read-only email lookup is the sudo-only exception: Settings renders it without paying a session lookup (the wunshot auth contract owns the lease rationale). The password-change drawer defaults `signOutAllSessions` off: passwordless-first users often set a password for the first time, and default-on would sign them out of the current device.

## Sessions list, no per-session revoke

Settings page lists sessions with device + geolocation context — formatted op-side, so the page never imports `#/email/…` itself (`email-layer-allowlist` would block it). Eviction UI is `signOutAll` only. Linted by `wunstart/no-single-session-revoke`.

The list is also the stale-device check: it covers every live session for the user, so a result with no `isCurrent` entry means this device has no live session — missing, revoked, expired, foreign, or unreadable — and the sessions handler clears both auth cookies and returns `[]`. The page then refreshes the router once, and the route guard redirects to sign-in. The call is a POST with a logout side effect — never load or prefetch it from a route loader or query prefetch. Reverify re-checks the live session before minting, so an evicted device cannot extend the access token beyond its remaining lifetime. This closes the window where the access token outlives its session.

Every identity transition calls `clearIdentityCache` (`components/auth/identity-cache.ts`) — sign-in/up, sign-out(s), account removal, and any flow that swaps the cookie pair for a different identity. React Query survives route changes and `userProfile` is `staleTime: Infinity`, so without the reset the next identity can see the previous user’s sessions, profile, or sudo-gated email, and an in-flight fetch can settle into the new mount. Cookies are shared across tabs while React Query is not, so the helper also writes a storage marker; `useAuthCacheSync` in the root clears the cache and refreshes the router in other open tabs. The sessions page still gates the empty state and redirect on `isFetchedAfterMount`, so only a response that completed after mount can act.

Ops that already call `verifyLiveSession` and their server fns use `runOpClearingDeadSession` (`middleware/_run-op.server.ts`): when that check throws `DeadSessionError`, the wrapper clears the dead cookies and rethrows — no extra read. `useDeadSessionRecovery` acts on the shared session-expired message alone: it clears the identity cache and invalidates the router so the guard redirects. A `requireAuth` 401 is not that signal — `verifyAuth` ends the pair on a definitively invalid token but keeps it when a ban or rate limit refused the refresh, and the status cannot tell the two apart, so that error surfaces in place and the retained pair restores the identity once the refusal lifts. `signOutAll` is the deliberate exception: its strict handler keeps the cookies on a dead session so a failed all-device sign-out cannot look successful, and the client only surfaces the error; the sessions-list check or the next auth refresh ends the identity.

Deployment note: create the production Hyperdrive configuration with caching disabled (`wrangler hyperdrive create … --caching-disabled`, or `update <id> --caching-disabled`). Caching is a configuration setting, not a binding field, and it is on by default; writes do not invalidate it, so a stale row can be served for the configured TTL. Session-liveness queries include `now()` and are uncacheable anyway — the stale-read risk is the identity and security reads, which must not be cached. If a cached configuration is added later for public reads, keep those reads on the disabled one. Create the config with the flag, and re-apply the update if it is ever re-created. The drift risk is a re-created config without the flag or a later cached config; if a deploy pipeline is added, include the update there.
