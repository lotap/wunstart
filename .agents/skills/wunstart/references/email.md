# Email verification + transport

Verify-before-create: no `users` row (email + hash PII) until a six-digit passcode proves inbox control. `email_verifications` table (active+archive pair) holds email + argon2id-hashed code (via DO, consistent with hash-secrets; small keyspace accepted) + attempts + expiry, keyed by email + entityId (anonId unauth, userId authed). Serves sign-up, sign-in notifications, password-change confirmations. No `emailVerifiedAt` on `users` — every existing user verified by construction.

- Form state (email, step) in `localStorage` with a short TTL matching code expiry (`Expiry.expiresAt` eviction). Server finds row by email + caller entityId. No verification cookie.
- Every code request returns `{expiresAt, resendAvailableAt}` — the row's expiry and the moment a resend is allowed — with identical UI step regardless of flow/registration (no enumeration). Copy differences (instructions-only email for sign-in/unknown: no code/links, creation stays behind sign-up form) visible only to inbox owner. Sign-in/unknown row still minted (timing uniformity + resend throttle; crossover to sign-up inside the reset window may transiently say "not ready").
- **Browser-bound anon codes:** anon-keyed rows verify against the anon cookie, so a code requested in one browser fails in another (or after the cookie is cleared). The code email and `PasscodeForm` state the constraint, and `requireAnonRegistered` returns a browser-mismatch message instead of a generic failure. User-keyed rows (`reverify`, email change) are not browser-bound.
- One verify op branches on account existence (sign-in branch preserves credential-ban/known-IP ordering + notification; creation branch keeps blanket ban check, reuses `createUser` from `_create-user.ts`). Returns whether account was created so sign-up form suppresses welcome on crossover. No intent param at verify; request-side `intent` literal only (`handleEmailRequestPasscode` input vs `handleEmailRequestPasscodeFromSession` hardcoded). Helpers split so future TOTP/passkey can interpose a grant step.
- Request paths split by middleware: unauthenticated sign-in/sign-up use `requireAnon`; account-email requests use `requireAuth`, and the email-change path re-checks sudo in the handler (the confirm op re-checks it again). Every user-keyed request verifies the live refresh session in the op, so a device revoked elsewhere cannot trigger account email, and reverify re-checks it before minting a new access token. `email_verifications` has no `intent` column; intent exists only on the request input.
- Re-request archives old intent, mints fresh (no separate resend op / `resendCount`). No cross-identity per-email cooldown (attackers would exhaust it); per-IP rate limit + failure-weight bans are the ceiling. Success activities log `ACTIVITIES_BASELINE_WEIGHT` by default; `emailRequestPasscode` overrides its own success `logging.weight` with `allowRatePerWindow(PASSCODE_SENDS_PER_WINDOW)` (`src/db/ops/auth/consts.ts`), so each send spends an equal share of the ban threshold and the next pre-check rejects once the window fills. A refused resend (`TOO_SOON_SINCE_LAST_RESET`) mails nothing and logs at weight 0, so it neither spends the send budget nor adds weight; the same per-IP limit caps the retry rate. Every success also carries the caller’s IP, so a NAT/CGNAT can ban that IP for the computed penalty (`calculatePenaltyTime`; retries extend toward `PENALTY_INTERVAL_MAX_QTY`) — the accepted cost of bounding cookie-dropping; the single `weight` column cannot scope success weight per ban arm. A user-keyed send (reverify, email change) carries the `userId` too, so the same weight counts toward the USER scope: the account itself can be banned, and its refresh is refused until the ban lifts, while the same sends’ IP ban blocks signing in again from that address. That self-ban is the price of the only per-account cap on account-email sends; removing it needs a per-scope weight mask on activities, not a lower weight.
- **Stale registered anon:** the `registered` claim can outlive its `anons` row (cross-database dev cookie, branch reset, archive race). `emailRequestPasscode` checks the live row before hashing and fails `ANON_NOT_FOUND` at weight 0; `handleEmailRequestPasscode` mints and registers a fresh anon, sets the cookie, and retries once. The `email_verifications.anon_id` FK is the race backstop. `retireAnon` tolerates a missing live row so sign-in/up still completes.

## Transport + delivery semantics

`EmailService` Effect service; config-selected transports: dev defaults Mailpit HTTP (`EMAIL_TRANSPORT` may select the Workers `send_email` binding or a fallback HTTP transport); prod defaults `send_email` with the fallback transport behind the `EMAIL_FALLBACK` chain. The in-tree fallback transport is an unverified example, not an endorsement — verify it or swap in your provider; deployment choice is yours. No console fallback — failed Mailpit send surfaces so dev notices. `emailLayer` is provided only at send sites: every server fn that can send provides it explicitly where it sends. The op-side invariant (consume-don't-construct) is owned by the wunshot auth contract; new send sites must add an explicit layer pass (review-visible; `wunstart/email-layer-allowlist` blocks email imports leaking into routes/components — it does not verify layer-passing at call sites, that's review). Kinds: `config` / `transient` / `rejected` / `ambiguous`; chain skips unconfigured, stops on permanent rejection, single whole-chain retry only when every hop provably didn't accept. `EMAIL_FROM`, `APP_URL`, `MAILPIT_URL`, `EMAIL_TRANSPORT`, `EMAIL_FALLBACK` (redacted/option) + your transport's own keys.

- Verification email is the deliverable: render pre-commit (render failure fails op, nothing committed); send failure fails op with `EMAIL_SEND` activity + retires the just-minted intent (guarded by passcode hash so concurrent reset survives) so immediate retry mints fresh instead of hitting `TOO_SOON_SINCE_LAST_RESET`. Exemplar flow: `components/auth/email-change.tsx` (request → verify → profile invalidation).
- Notifications (sign-in, password-change, session-reuse) are best-effort post-commit: render + send after commit inside `Effect.ignore({log: true})`; render/send/db/defect failures logged, never fail op, never retry, never persist (no outbox table/queue — would persist plaintext passcode, violating hash-secrets; archive would retain PII email content). `EMAIL_SEND` metadata stores transport + code only, never bodies/tokens.
- Templates: react-email, line 1 `// @refresh reset`, default export (email-dev requires), static `X.PreviewProps` behind `// SAFETY:` cast, named `renderX()` returning `{subject, html, text}` via dual `Promise.all` render. `<Tailwind config={emailTailwindConfig}>` hex-only (v4 oklch breaks inliner; tokens duplicated from shadcn). Preview `dev:email` on :3001. `resolveEmailTimezone` / `formatEmailTime` (America/New_York fallback, Intl + abbrev), `formatLocation` (`XX` → null). All templates render through `src/email/components/email-layout.tsx`: tinted page, 640px card, a wordmark built from `APP_URL` plus the `wordmarkPath` constant (absolute URL, so `APP_URL` must be public in production), and a shared footer. Rebranding replaces the asset and updates `wordmarkPath`. Inter is declared but never loaded; the system stack is the real fallback. Security/account mail contains no links or CTAs — codes and typed URLs only. Emails are light-only (`color-scheme`/`supported-color-schemes` meta): do not add a dark wordmark swap, because `prefers-color-scheme` can report dark while the card stays light; a full dark variant is the only reliable form and Gmail/Outlook ignore it. PreviewProps read `src/email/preview.ts`, which points at the app on `http://localhost:3000`; the preview wordmark is served by the app, so run `dev` alongside `dev:email`.
