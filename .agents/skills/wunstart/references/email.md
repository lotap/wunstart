# Email verification + transport

Verify-before-create: no `users` row (email + hash PII) until a 6-digit passcode proves inbox control. `email_verifications` table (active+archive pair) holds email + argon2id-hashed code (via DO, consistent with hash-secrets; small keyspace accepted) + attempts + expiry, keyed by email + entityId (anonId unauth, userId authed). Serves sign-up, sign-in notifications, password-change confirmations. No `emailVerifiedAt` on `users` — every existing user verified by construction.

- Form state (email, step) in `localStorage` with a short TTL matching code expiry (`Expiry.expiresAt` eviction). Server finds row by email + caller entityId. No verification cookie.
- Every code request returns `{expiresAt}` with identical UI step regardless of flow/registration (no enumeration). Copy differences (instructions-only email for sign-in/unknown: no code/links, creation stays behind sign-up form) visible only to inbox owner. Sign-in/unknown row still minted (timing uniformity + resend throttle; crossover to sign-up within ~1 min may transiently say "not ready").
- One verify op branches on account existence (sign-in branch preserves credential-ban/known-IP ordering + notification; creation branch keeps blanket ban check, reuses `createUser` from `_create-user.ts`). Returns whether account was created so sign-up form suppresses welcome on crossover. No intent param at verify; request-side `intent` literal only (`handleEmailRequestPasscode` input vs `handleEmailRequestPasscodeFromSession` hardcoded). Helpers split so future TOTP/passkey can interpose a grant step.
- Re-request archives old intent, mints fresh (no separate resend op / `resendCount`). No per-email cooldown (attackers would exhaust it); per-IP rate limit + failure-weight bans are the ceiling. `Password` validator extracted to `#/isomorphic/validators.ts`; `successWeight` on `createOpsFn` deferred (intent requests log weight 1; 5/min IP limit is the ceiling).

## Transport + delivery semantics

`EmailService` Effect service; config-selected transports: dev defaults Mailpit HTTP (`EMAIL_TRANSPORT` may select the Workers `send_email` binding or a fallback HTTP transport); prod defaults `send_email` with the fallback transport behind the `EMAIL_FALLBACK` chain. The in-tree fallback transport is an unverified example, not an endorsement — verify it or swap in your provider; deployment choice is yours. No console fallback — failed Mailpit send surfaces so dev notices. `emailLayer` provided ONLY where email sends (sending ops call `EmailService.send` directly; layer provisioned in code request/verify fns, `handlePasswordSignIn`, `handlePasswordChange`, refresh-path revoked notification). The op-side invariant (consume-don't-construct) is owned by the wunshot auth contract; new send sites must add an explicit layer pass (review-visible; `wunstart/email-layer-allowlist` blocks email imports leaking into routes/components — it does not verify layer-passing at call sites, that's review). Kinds: `config` / `transient` / `rejected` / `ambiguous`; chain skips unconfigured, stops on permanent rejection, single whole-chain retry only when every hop provably didn't accept. `EMAIL_FROM`, `APP_URL`, `MAILPIT_URL`, `EMAIL_TRANSPORT`, `EMAIL_FALLBACK` (redacted/option) + your transport's own keys.

- Verification email is the deliverable: render pre-commit (render failure fails op, nothing committed); send failure fails op with `EMAIL_SEND` activity + retires the just-minted intent (guarded by passcode hash so concurrent reset survives) so immediate retry mints fresh instead of hitting `TOO_SOON_SINCE_LAST_RESET`. Exemplar flow: `components/auth/email-change.tsx` (request → verify → profile invalidation).
- Notifications (sign-in, password-change, session-reuse) are best-effort post-commit: render + send after commit inside `Effect.ignore({log: true})`; render/send/db/defect failures logged, never fail op, never retry, never persist (no outbox table/queue — would persist plaintext passcode, violating hash-secrets; archive would retain PII email content). `EMAIL_SEND` metadata stores transport + code only, never bodies/tokens.
- Templates: react-email, line 1 `// @refresh reset`, default export (email-dev requires), static `X.PreviewProps` behind `// SAFETY:` cast, named `renderX()` returning `{subject, html, text}` via dual `Promise.all` render. `<Tailwind config={emailTailwindConfig}>` hex-only (v4 oklch breaks inliner; tokens duplicated from shadcn). Preview `dev:email` on :3001. `resolveEmailTimezone` / `formatEmailTime` (America/New_York fallback, Intl + abbrev), `formatLocation` (`XX` → null).
