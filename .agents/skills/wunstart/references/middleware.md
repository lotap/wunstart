# Middleware + server functions

## The static-import landmine

Middleware modules must NOT statically import request-bound op modules — the middleware loads them via `await import()` inside `.server()` (the current set is visible at those call sites); `import type` at top is fine (erased). Static layers (`dbLayer`, `authLayer`), error classes (`AuthTokenError`, `RateLimitError`, `isOpsError`), and `signAnon` (jose + Config only) stay static — proven safe. A static value import of a request-bound op made the middleware `undefined` during TanStack's early `flattenMiddlewares` graph build → opaque `TypeError: Cannot read properties of undefined (reading 'options')`. ESM caches `import()` — no memoization needed. Linted by `wunstart/no-static-workers-import-in-middleware`. Dead end, don't re-try: deferring Hyperdrive access via `Layer.unwrap` was reverted (top-level `import {env}` is fine per Cloudflare docs). If a new op transitively needs the hashing stub / service bindings, add it to the lint's module list and import it dynamically.

## Chain

`start.ts` order is deliberate. Request: `[csrfMiddleware (server-fn only), sanitizeErrors]`. Function: `[serverFnNoStore, createRateLimit(150), verifyAnon, rejectDegradedAuth]` — `rejectDegradedAuth` last so server fns never see degraded state. `verifyAnon(type: function).middleware([verifyAuth])`, `verifyAuth.middleware([getRequestInfo])` → every fn gets `{ip, ua, country, city, region, timezone, auth, anon}`. Anon issuing is inline in `verifyAnon` handler (`signAnon` + `setAnonCookie`), not a separate middleware.

- Chained: `.middleware([getRequestInfo])` → typed context. Standalone (`createMiddleware({type: 'function'})`): context typed `undefined` → `const ctx: unknown = context` then `ctx as GlobalServerFnContext` behind `// SAFETY:` (require-*, rejectDegradedAuth pattern).
- Identity decision table: `AuthTokenError` from the refresh check = definitively invalid → clear cookies, go anon. `RateLimitError` → keep cookies, go anon. Anything else incl. defects → `{status: 'degraded'}` → 503 before any server fn. `KnownServerError` first statement of every catch, rethrown untouched. An access JWE that is merely expired is still `AuthTokenError`, so `verifyAuth` falls through to the refresh cookie; its `EXPIRED_JWE` activity carries weight 0. An unknown `kid` is treated as the weight-0 rotation state; for access, refresh, and Anon token verdicts, only a known-`kid` verification failure stays charged, while grace verdicts are weight 0. Auth/anon contexts status-discriminated `'authenticated'` / `'verified'`, `null` = none.
- `verify-auth`: needs access + refresh else refresh-only path; success rotates both + deletes anon cookie. `verify-anon`: degraded auth → degraded anon (no issue on outage); authed → `anon: null`; else verify anon JWT → verified, else `signAnon` + `setAnonCookie`; sign failure → degraded. `rejectDegradedAuth` → 503 `KnownServerError`. `requireAuth` (401) / `requireAnon` (400 if authed) / `requireAnonRegistered` (400 if authed, then `anon.registered`): read already-verified ctx, no re-verify, no degraded logic.
- `get-request-info`: `ip = cf-connecting-ip (validated) ?? runtime socket (validated) ?? DEV loopback ('127.0.0.1', development only)`; production fails closed with 503 before any op when no valid client IP resolves. Only `cf-connecting-ip` is trusted (Cloudflare overwrites it); `X-Forwarded-For`/`Forwarded` are never read. `SYSTEM_OPS_IP` ('0.0.0.0') is reserved for `createSystemOpsFn` and does not satisfy a known-IP bypass; the HTTP boundary rejects it as a request address, so the ban pipeline only sees resolved client addresses. A deployment that can reach the app without a trusted client IP must supply a trusted header; a per-deployment source setting is deferred. Keep the full address in `context.ipAddress`: it is stored and displayed in Settings and security emails; IPv6 `/64` normalization belongs only inside the limiter. The only loopback substitution is the development fallback above. `ua.slice(0, 512)`; `country = cf-ipcountry || 'XX'` sentinel, city/region null if absent, percent-decoded + length-capped, timezone IANA-validated. The limiter keys IPv6 by `/64` after expanding an embedded IPv4 tail, and folds IPv4-mapped addresses onto the wrapped IPv4 key.
- `sanitize-errors` (request): ops-contract → 422 client-safe message; `KnownServerError` passthrough, thrown through `throwKnownServerError(status, message)` at the boundary (ops use `opsFailure`); else generic 500, cause preserved.
- Cache policy: every server-fn response defaults to `Cache-Control: no-store` (`serverFnNoStore`) because a server fn carries identity, session state, or an action result; a GET with no directive is still eligible for heuristic caching, and cookies do not make a response private. The default is set before `next()` so a genuinely public, cacheable endpoint can override it from its own middleware or handler and own the full policy, including `Vary`; never opt in by removing the global default.
- Rate-limit: in-memory per-IP weighted window (`rate-limit.ts`). `start.ts` installs the global limiter; the opt-in per-fn `rateLimit` shares the global key. `allowPerWindow(max)` derives each request's weight from the shared threshold. `REFRESH_ATTEMPTS_PER_MINUTE` is consumed before a fallback refresh so a dead pair cannot turn a request stream into unbounded refresh ops and activity rows; the lane is per-IP and runs before the token is verified, so a shared egress can see its clients’ fallback 429 after a dead pair fills the lane — per-session keying would need the verification the lane exists to bound. `signOutRateLimit` bounds the sign-out Argon2 nonce check. Both scoped lanes use their own keys and do not spend the global/auth budget. `addRateLimitEvent` and `createRateLimit` take an optional `scope` that namespaces the IP key. Not shared across isolates — defense-in-depth only; an edge rate limit is the distributed guarantee. Op `RateLimitError` forwarded as extra event (can 429).

## Server-fn shape

`handle-*.ts`: mutations `createServerFn({method: 'POST'})`, reads `{method: 'GET'}` (`handle-get-*`, all zero-input — identity comes from ctx; reads carrying params are POST-shaped fns) → `.middleware([rateLimit?, require*])` → `.validator(Schema.toStandardSchemaV1(...))` (never deprecated `inputValidator`; schemas live in `#/isomorphic/validations/`, shared client/server, never inline) → `.handler(({data, context}) => runOp({op, data: {ids from ctx, ipAddress}, layers: [authLayer, dbLayer(, emailLayer)]}) + cookie side-effects)`. Return type inferred — convert with `DateTime.toDate(...)` on the way out (see `handle-verify-auth.ts`). No id params — if a `ById` fn becomes necessary, name it `...ById` + authorize it (the name is convention only — authorization is review-enforced, nothing checks it). A read that can change server state (the sessions list ends a dead session) uses POST and is named for the resource, not `handle-get-*`; the response is still the query payload. Exemplars: read path `handle-get-user-profile.ts`; mutation path `handle-sign-out.ts` + `hooks/use-sign-out.ts`.

- `runOp` (`middleware/_run-op.server.ts`, `createServerOnlyFn`): `{op, data, layers}` → `Effect.provide` + `runPromise`. Layers per run (generics fail if incomplete). `dbLayer` lazy pool (no connect on build; `DATABASE_URL` else Hyperdrive via lazy `cloudflare:workers` import — DB only in CF runtime). `authLayer` (`id:secret` CSV configs incl. dedicated grace-token JWE secrets). `emailLayer` dev/prod. `HashingStub.layer(name)` (userId else anonId, `AUTH_HASHER.idFromName`) provided inside the op, not via `runOp`.
- Pre-check dedup: `checkCurrentBansAndExcessiveActivities(targets)` stashes 12-arm union; logger reuses via `Ref.getAndSet`; fresh-vs-stale compensated with extra weight.
- Cookies: httpOnly, lax, `/`, `secure = PROD`, `Path=/`. Production defaults to host-only `__Host-Http-` names with no `Domain`; development does not need `VITE_COOKIE_DOMAIN`. OWASP’s Session Management Cheat Sheet recommends `__Host-` for session IDs; `__Host-Http-` is that host-only rule plus the browser-enforced `HttpOnly`/`Set-Cookie` requirement. Setting `VITE_COOKIE_DOMAIN` in a production build is the subdomain-sharing opt-in: names switch to `__Http-` and the cookie gets that `Domain`, so every subdomain under it can set the cookie — only do that when all subdomains are fully trusted. The prefix is browser-enforced where supported; omitting `Domain` is the backstop. Dev uses plain names plus the per-branch `VITE_COOKIE_SUFFIX` (cookies ignore ports and worktrees share `localhost`; no cookie domain is needed). Helpers: `setAuthCookies` / `setAnonCookie` (`middleware/_set-*.ts`); names and scope from `_cookie-config.ts`. Auth-issue deletes anon; sign-out deletes auth + issues anon. Per-worktree secret sets and `<branch>.localhost` were considered; the suffix is the contained fix, and signature-level separation belongs to the deferred production secret generator.
